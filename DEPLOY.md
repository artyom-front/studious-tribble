# 🏆 Production Deployment Guide — «Футбол Чувашии» (SCORES21)

**Полноценный гайд для деплоя как у серьёзного взрослого проекта.**
Понятно даже гуманитарию: каждый шаг — что делаем, **зачем** это надо и как проверить, что получилось.
Один путь, без развилок: **GitHub → Docker → PostgreSQL → Nginx + SSL → автодеплой**.

---

## 📋 Что входит в «золотой стандарт»

| Компонент | Инструмент | Зачем |
|---|---|---|
| **База данных** | PostgreSQL 16 | Надёжная БД для конкурентных запросов, бэкапов `pg_dump` и роста данных |
| **Version Control** | Git + GitHub | Хранение кода, история изменений, командная работа |
| **CI** | GitHub Actions | Автотесты на каждый push: не даём сломать main |
| **CD** | GitHub Actions + GHCR | Автосборка Docker-образа и автодеплой на сервер по тегу |
| **Containerization** | Docker | Приложение запускается «как у разработчика» — на любом сервере |
| **Orchestration** | Docker Compose | Поднимает связку «приложение + PostgreSQL» одной командой |
| **Reverse Proxy** | Nginx | Принимает трафик из интернета, раздаёт сжатие и кэш статики |
| **SSL/HTTPS** | Let's Encrypt (certbot) | Бесплатный сертификат с автопродлением |
| **Backup** | cron + pg_dump | Ежедневная копия базы, защита от потери данных |
| **Security** | 2FA (TOTP) + RBAC + rate limit | Защита админки и аккаунтов |
| **SEO** | SSR + sitemap.xml + robots.txt | Поисковики видят контент и индексируют сайт |
| **Tests** | Bun test (54 unit + 16 integration) | Проверка бизнес-правил: дисквалификации, таблицы, 2FA |

---

## 🧠 Как это всё устроено (30 секунд теории)

Поток деплоя выглядит так:

```
 ваш компьютер                GitHub                        сервер (VPS)
 ─────────────    ───────────────────────────    ─────────────────────────────
 git tag v1.0.0  →  Actions собирает Docker-образ  →  deploy.sh по SSH:
 git push          и кладёт его в реестр GHCR        1. бэкап БД (pg_dump)
                   перед этим прогоняет тесты        2. миграции (prisma db push)
                                                     3. docker compose up -d
                                                     4. health-check (90 сек)
                                                     5. авто-откат, если упал
```

**Почему образ, а не `git pull` на сервере?** Образ — это «запечатанная» сборка: та же версия,
которая прошла тесты в CI. Сервер ничего не компилирует, а просто скачивает готовый артефакт.
Так деплой занимает секунды, а откат на старую версию — одну команду.

**Почему деплой запускается тегом, а не каждым push?** Обычный push в main прогоняет только
тесты (CI). Поставка на прод — осознанное решение, поэтому для неё вы выпускаете **версию**:
`git tag v1.0.1 && git push origin v1.0.1`.

## 🚀 Пошаговый деплой

### Шаг 1. Купить сервер (5 минут)

Заходим на **timeweb.cloud → Cloud → Создать**:

- **ОС:** Ubuntu 24.04 (LTS — долгая поддержка, больше всего гайдов)
- **Тариф:** 2 ГБ RAM / 20 ГБ SSD / 1 vCPU (~250 ₽/мес)
- **Регион:** Москва (ближе к игрокам и болельщикам — меньше пинг)

**Зачем 2 ГБ:** на сервере одновременно будут жить PostgreSQL (кэширует данные в RAM),
Next.js (серверный рендеринг страниц) и сборка Docker-образа — 1 ГБ впритык не хватит.

После создания панель покажет **IP-адрес** и **root-пароль** — сохраните их.
Root — это главный пользователь сервера, как «администратор Windows».

### Шаг 2. Направить домен на сервер (5 минут)

DNS — «телефонная книга интернета»: когда человек вводит `scores21.ru`, браузер спрашивает
у DNS «какой IP у этого имени?». Мы должны ответить: «вот IP моего сервера».

В панели регистратора домена (Reg.ru / Timeweb → **DNS-управление**) добавьте записи:

| Тип | Имя | Значение | TTL |
|---|---|---|---|
| A | `@` | IP-адрес сервера из шага 1 | 3600 |
| CNAME | `www` | `scores21.ru.` | 3600 |

- `@` означает «сам домен без поддомена» (`scores21.ru`)
- запись `www` говорит: «www.scores21.ru — это тот же сайт»

**Проверка** (запускается и на вашем компьютере; обновление DNS занимает от минуты до часа):

```bash
ping scores21.ru
# Должно отвечать с IP-адреса вашего сервера
```

### Шаг 3. Подключиться к серверу (3 минуты)

```bash
ssh root@ВАШ_IP
# первый раз спросит fingerprint — наберите yes
# затем пароль root из шага 1
```

**Что такое SSH:** защищённый терминал «внутрь сервера». Всё дальнейшее делается в нём.
Строка приглашения сменится с `user@laptop` на `root@vps-...` — значит, команды
исполняются уже на сервере.

### Шаг 4. Установить софт на сервер (10 минут)

```bash
# 1. Обновить систему: подтянуть свежие патчи безопасности
apt update && apt upgrade -y

# 2. Docker: запуск приложения в контейнерах
#    (зачем: приложение live в «пузыре» со своими зависимостями —
#     не конфликтует с системой, обновляется заменой образа)
curl -fsSL https://get.docker.com | sh

# 3. Nginx: обратный прокси — принимает трафик из интернета,
#    отдаёт HTTPS, сжимает текст и кэширует статику
apt install -y nginx

# 4. Certbot: получение и автопродление SSL-сертификатов Let's Encrypt
apt install -y certbot python3-certbot-nginx

# 5. Git: чтобы скачать код проекта на сервер
apt install -y git

# Проверка: всё должно показать версии
docker --version && nginx -v && certbot --version && git --version
```

### Шаг 5. Забрать код проекта на сервер (3 минуты)

```bash
git clone https://github.com/artyom-front/studious-tribble.git /opt/scores21
cd /opt/scores21
```

**Почему `/opt`:** системное место для сторонних приложений (не `/home` для людей
и не `/etc` для настроек системы). Так принято «у взрослых».

В репозитории уже лежат все файлы деплоя:

| Файл | Роль |
|---|---|
| `deploy/docker-compose.prod.yml` | Описание прод-стека: PostgreSQL + приложение |
| `deploy/nginx.conf` | Готовый конфиг nginx: проксирование, gzip, кэш, заголовки |
| `scripts/deploy.sh` | Скрипт поставки: бэкап → миграции → запуск → проверка |
| `scripts/backup-db.sh` | Ежедневный бэкап базы (pg_dump) |
| `prisma/schema.prisma` | Схема БД: 15 таблиц домена (лица, команды, матчи…) |
| `.github/workflows/ci.yml`, `cd.yml` | Автотесты и автодеплой на стороне GitHub |

### Шаг 6. Создать файл секретов `.env` (5 минут)

Файл `.env` хранит пароли и ключи. Он **никогда не попадает в git** (уже в `.gitignore`) —
секреты должны существовать только на сервере.

```bash
cp .env.example .env
nano .env
```

Заполните построчно (сохранение в nano: `Ctrl+X`, затем `Y`, затем `Enter`):

```ini
# Пароль PostgreSQL. Придумайте длинный или сгенерируйте командой:
#   openssl rand -hex 16
POSTGRES_PASSWORD=СТРОКА_ИЗ_32_СИМВОЛОВ

# Ключ подписи cookie-сессий. Уникален для сайта: кто знает ключ —
# тот может подделать сессии. Сгенерируйте:
#   openssl rand -hex 32
AUTH_SECRET=СТРОКА_ИЗ_64_СИМВОЛОВ

# Логин и пароль первого администратора портала.
# Создаются автоматически при первом деплое, дальше входите по ним в /admin.
ADMIN_EMAIL=admin@scores21.ru
ADMIN_PASSWORD=ПАРОЛЬ_АДМИНА_МИНИМУМ_8_СИМВОЛОВ

# Публичный адрес сайта: влияет на sitemap.xml, canonical-ссылки и cookies
SITE_URL=https://scores21.ru

# Не показывать демо-аккаунты на странице входа (в проде — обязательно 0)
SHOW_DEMO_ACCOUNTS=0
```

> `DATABASE_URL` (адрес базы) писать не нужно — его автоматически собирает
> docker-compose из `POSTGRES_PASSWORD` при старте контейнеров.

Закройте доступ посторонним:

```bash
chmod 600 .env   # читать может только root
```

### Шаг 7. Настроить nginx и получить SSL-сертификат (10 минут)

Копируем готовый конфиг и подставляем свой домен:

```bash
# 1. Забрать конфиг из репозитория
cp deploy/nginx.conf /etc/nginx/sites-available/scores21

# 2. Заменить домен-заглушку на ваш (scores21.ru → ваш домен)
sed -i 's/scores21.ru/ВАШ_ДОМЕН.ru/g' /etc/nginx/sites-available/scores21

# 3. Включить сайт (символическая ссылка = «nginx, смотри этот конфиг»)
ln -sf /etc/nginx/sites-available/scores21 /etc/nginx/sites-enabled/

# 4. Проверить конфиг на ошибки и перечитать
nginx -t && systemctl reload nginx
```

Теперь получаем бесплатный HTTPS-сертификат:

```bash
certbot --nginx -d ВАШ_ДОМЕН.ru -d www.ВАШ_ДОМЕН.ru
```

- Certbot проверит, что домен действительно указывает на этот сервер (шаг 2)
- Выпустит сертификат Let's Encrypt и сам допишет SSL-настройки в конфиг nginx
- Включит автопродление (сертификаты живут 90 дней — продлеваются сами)

**Проверка** (с вашего компьютера):

```bash
curl -I https://ВАШ_ДОМЕН.ru
# HTTP/2 502 — это НОРМАЛЬНО: nginx работает и HTTPS есть,
# но приложение ещё не запущено (запустим на шаге 9)
```

### Шаг 8. Дать GitHub Actions доступ к серверу (5 минут)

Деплой должен происходить **без вас**: GitHub сам зайдёт на сервер по SSH и обновит версию.
Для этого нужен отдельный SSH-ключ — только для деплоя (ваш личный ключ не светим).

**На сервере** (в сеансе root):

```bash
# 1. Создать отдельную пару ключей для деплоя
#    -N "" = без парольной фразы (CI не сможет её вводить)
ssh-keygen -t ed25519 -f ~/.ssh/deploy_key -N ""

# 2. Разрешить вход по этому ключу
cat ~/.ssh/deploy_key.pub >> ~/.ssh/authorized_keys

# 3. Показать ПРИВАТНЫЙ ключ — его скопируем в GitHub (полностью, с первой
#    строки -----BEGIN до последней -----END)
cat ~/.ssh/deploy_key
```

**На GitHub** → репозиторий → **Settings → Secrets and variables → Actions → New repository secret**.
Добавьте 4 секрета:

| Имя секрета | Значение | Зачем |
|---|---|---|
| `DEPLOY_HOST` | IP-адрес сервера | Куда подключаться |
| `DEPLOY_USER` | `root` | Под кем заходить |
| `DEPLOY_SSH_KEY` | приватный ключ из `cat ~/.ssh/deploy_key` | Чем авторизоваться |
| `DEPLOY_PUBLIC_URL` | `https://ВАШ_ДОМЕН.ru` | Финальная проверка сайта после деплоя |

Секреты видны только GitHub Actions — в коде и логах они показываются как `***`.

### Шаг 9. Запустить деплой (2 минуты + ~7 минут сборки)

Всё готово: сервер настроен, ключи выданы. Теперь **на своём компьютере**,
в папке проекта, объявляем первую версию:

```bash
git tag v1.0.0
git push origin v1.0.0
```

Откройте на GitHub: **Actions → CD** — вы увидите живой пайплайн:

1. **Build & push** — сборка Docker-образа и публикация в реестр GHCR (2–5 мин)
2. **Deploy → VPS** — заход на сервер и запуск `scripts/deploy.sh` (1–2 мин)
3. **Health-check** — GitHub проверяет, что сайт отвечает (до 60 сек)

Зелёные галочки на всех трёх — сайт в продакшене. 🎉

### Шаг 10. Что деплой делает сам (под капотом)

`scripts/deploy.sh` — сердце поставки. Его шаги и их смысл:

| # | Шаг | Зачем |
|---|---|---|
| 1 | `pg_dump` → `backups/pg-*.dump` | Снимок базы **до** любых изменений: если новая версия сломает схему — восстановимся за минуту |
| 2 | `prisma db push` | Актуализирует таблицы под текущую схему (новые поля/индексы) без потери данных |
| 3 | `docker compose up -d` | Поднимает PostgreSQL и новую версию приложения; старый контейнер заменяется |
| 4 | health-check `/api/health`, 90 сек | Приложение обязано доказать, что живо и БД отвечает |
| 5 | `prisma/bootstrap.ts` | Один раз создаёт администратора из `ADMIN_EMAIL`/`ADMIN_PASSWORD` (при следующих деплоях пропускается) |
| 6 | Запись в `.deploy/history` | История версий — по ней работает откат |

**Если health-check не прошёл** — скрипт автоматически откатывается на предыдущую
рабочую версию. Прод не «лежит в ожидании админа», а продолжает работать на старой версии.

### Шаг 11. Первый вход и включение 2FA (3 минуты)

Откройте `https://ВАШ_ДОМЕН.ru/admin` и войдите:

- **email** — из `ADMIN_EMAIL`
- **пароль** — из `ADMIN_PASSWORD`

Сразу сделайте два действия (панель → **Система → Безопасность**):

1. **Смените пароль** на свой — пароль из `.env` больше не нужен
2. **Включите 2FA** — отсканируйте QR-код приложением (Google Authenticator /
   Яндекс.Ключ) и **сохраните 8 резервных кодов** (выдаются один раз)

Двухфакторка защищает от украденного пароля: для входа нужен ещё и код из телефона,
меняющийся каждые 30 секунд. Стандарт RFC 6238, анти-replay, брутфорс-лимиты — уже внутри.

### Шаг 12. Включить ежедневный бэкап (3 минуты)

```bash
crontab -e
# Добавить строку (каждый день в 03:15 ночью, когда трафика почти нет):
15 3 * * * /opt/scores21/scripts/backup-db.sh >> /var/log/scores21-backup.log 2>&1
```

Скрипт сам делает: `pg_dump` (снимок базы в сжатом формате) → ротацию (хранит 30 дней,
старше — удаляет). Проверить, что бэкап появился, можно утром:

```bash
ls -lh /opt/scores21/backups/
# pg-20260903-031500.dump  ~200K  — копия базы на месте
```

### Шаг 13. Финальная проверка (5 минут)

| URL | Что должно быть |
|---|---|
| `https://ВАШ_ДОМЕН.ru` | Livescore: матчи, турнирная таблица |
| `https://ВАШ_ДОМЕН.ru/admin` | Форма входа → панель управления |
| `https://ВАШ_ДОМЕН.ru/sitemap.xml` | XML-карта сайта для поисковиков |
| `https://ВАШ_ДОМЕН.ru/robots.txt` | Правила индексации (закрыт `/admin`) |
| `https://ВАШ_ДОМЕН.ru/api/public/overview` | JSON со списком лиг (REST API) |

Проверка HTTPS-оценки: `curl -I https://ВАШ_ДОМЕН.ru` → `HTTP/2 200`. Всё — деплой завершён.

## 🔄 CI/CD: что происходит без вашего участия

**Обычный push в main** (когда вы пишете код) — работает **CI**:

| Job | Что делает | Время |
|---|---|---|
| quality | ESLint (стиль кода) + TypeScript (типы) + 54 юнит-теста движков | ~1 мин |
| integration | Чистый PostgreSQL + демо-данные + прод-сборка + 16 интеграционных тестов (36 инвариантов PRD: дисквалификации, техпоражения, 2FA, SSR/SEO) | ~3 мин |
| docker | Сборка Docker-образа (проверка, что соберётся и в CI) | ~2 мин |
| audit | Проверка зависимостей на известные уязвимости | ~30 сек |

Красный CI на PR = код не попадёт в main, пока не исправлен. Это «страховка» продакшена.

**Тег `v*`** (когда вы выпускаете версию) — работает **CD** (шаги 9–10 выше).

## 📦 Как выпускать обновления

Жизненный цикл правки (тот же «золотой стандарт», что у больших команд):

```bash
# 1. Ветка под задачу
git checkout -b feature/live-protocol
# ... правки кода ...
git add . && git commit -m "Протокол: кнопка завершения матча"

# 2. Pull Request на GitHub → CI прогоняет тесты → merge в main

# 3. Выпуск версии (деплой поедет сам)
git tag v1.0.1
git push origin main --tags
```

Номер версии — семантика: `v1.0.1` точечная правка, `v1.1.0` новая фича, `v2.0.0` ломающие изменения.

**Экстренный откат** (если новая версия всё-таки плохая, а CI не поймал):

```bash
# На сервере: вернуть предыдущую рабочую версию
cd /opt/scores21 && ./scripts/rollback.sh
```

## 💾 Восстановление из бэкапа

Допустим, база повреждена (или удалили важные данные). План:

```bash
cd /opt/scores21

# 1. Остановить приложение (чтобы никто не писал в базу во время восстановления)
docker compose -f deploy/docker-compose.prod.yml stop app

# 2. Посмотреть, какой бэкап восстанавливаем
ls -lh backups/

# 3. Залить его в PostgreSQL (pg_restore пересоздаёт данные из дампа)
docker compose -f deploy/docker-compose.prod.yml exec -T db \
  pg_restore -U scores21 -d scores21 --clean --if-exists < backups/pg-ДАТА.dump

# 4. Запустить приложение обратно
docker compose -f deploy/docker-compose.prod.yml up -d
```

> `--clean --if-exists` = перед восстановлением снести текущие таблицы,
> чтобы не было конфликтов дублей. База станет ровно такой, какой была на момент бэкапа.

## 🩺 Если что-то сломалось (диагностика)

| Симптом | Вероятная причина | Что выполнить |
|---|---|---|
| `502 Bad Gateway` | Приложение не поднялось | `docker logs scores21-app --tail 50` |
| `502` + в логах про БД | PostgreSQL не готов / пароль | `docker logs scores21-db --tail 30`, проверьте `POSTGRES_PASSWORD` в `.env` |
| Сайт не открывается по домену | DNS ещё не обновился | `ping ВАШ_ДОМЕН.ru` (шаг 2), подождите до часа |
| «Сертификат недействителен» | Certbot не продлился | `certbot certificates`, затем `certbot renew --dry-run` |
| Красный job Deploy в Actions | Нет секретов / сменился IP | Settings → Secrets (шаг 8); `ssh root@IP` вручную |
| `git clone` на сервере просит пароль | Репозиторий приватный | Сделайте его public или клонируйте с токеном (GitHub → Settings → Developer settings → PAT) |
| Деплой прошёл, но данные пропали | Смотрели не ту БД | `docker compose -f deploy/docker-compose.prod.yml exec db psql -U scores21 -d scores21 -c 'SELECT count(*) FROM "Match";'` |

Универсальная последовательность «что смотреть сначала»:

```bash
docker compose -f deploy/docker-compose.prod.yml ps   # кто жив, кто мёртв
docker logs scores21-app --tail 100                   # что говорит приложение
docker logs scores21-db --tail 30                     # что говорит база
cat /opt/scores21/.deploy/history                     # какие версии ставились
```

Перезапуск «с нуля» (данные в БД сохраняются):

```bash
cd /opt/scores21
docker compose -f deploy/docker-compose.prod.yml down
./scripts/deploy.sh $(cat .deploy/current)
```

## 💻 Локальная разработка (для будущей команды)

Разработчику не нужен прод-сервер — всё запускается на своём компьютере:

```bash
git clone https://github.com/artyom-front/studious-tribble.git
cd studious-tribble

# 1. Поднять PostgreSQL в докере (порт 5432)
docker compose up -d db

# 2. Создать таблицы по схеме и залить демо-данные
#    (лиги, матчи, игроки, демо-аккаунты admin@ff21.ru и др.)
cp .env.example .env   # DATABASE_URL для локалки уже указан в .env.example
bunx prisma db push
bun prisma/seed.ts

# 3. Запустить дев-сервер
bun install
bun run dev            # http://localhost:3000
```

Демо-аккаунты (только в деве): `admin@ff21.ru`, `liga@ff21.ru`, `sudya@ff21.ru`,
`club@ff21.ru` — пароли в `prisma/seed.ts`.

Карта кода: `src/lib/engine/*` — бизнес-движки (расписание, дисциплина, таблицы);
`src/app/api/**` — REST API; `src/app/(site)/**` — SSR-страницы; `prisma/schema.prisma` — модель данных.
